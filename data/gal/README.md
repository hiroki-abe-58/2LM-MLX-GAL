# ギャルLINE会話コーパス（架空データ）

「自分でデータセットを作って、モデルにキャラクターを持たせる」ための教材用データセットです。
実在の人物・会話とは一切関係のない、完全な架空データです。

## 何をするものか

公開データセットだけで学習した素の `2LM` は、敬語まじりの機械翻訳調で喋ります。
元にした対話データが、英語を機械翻訳したものと、大きなモデルに書かせた合成データだからです。
**モデルの人格は、データの人格です。** 口調を変えたければ、データの口調を変えるしかありません。

このスクリプトは、その「変えるためのデータ」を手元で作ります。

## 会話文を人間が書いていない理由

会話文はローカルで動かした **Qwen2.5-32B-Instruct（Apache-2.0）** に書かせています。
人間が書いていないのは、手間の問題だけではありません。

**ライセンスの問題があります。** 作ったデータセットと、そこから学習した重みを配布するなら、
生成に使ったモデルの利用条件を確認しなければいけません。商用のチャットサービスの規約には、
出力を使ってモデルを学習させることを禁じる条項が置かれているのが普通です。
「小さいモデルだから競合しない」という言い分は、条文に書かれていない限り抗弁になりません。

Apache-2.0 のモデルには出力の利用条件がありません。だからローカルで完結させています。
このプロジェクトが既に学習に使っている `llm-jp/magpie-sft-v1.0` も
`Aratako/Magpie-Tanuki-8B-97k` も、Apache-2.0 のモデルが書いた合成データです。
**同じ筋を通しているだけ**で、特別なことはしていません。

**再現できるという利点もあります。** 課金が前提の手順は、読者の半分が実行できません。

## 作りかた

3段階に分かれています。

```bash
# 1. 話題を出させる（数分）
python data/gal/generate.py --stage topics

# 2. 会話を書かせる（時間がかかる。止めても再開できる）
python data/gal/generate.py --stage pairs --target 4000

# 3. 検査してまとめる（一瞬）
python data/gal/generate.py --stage build
```

`--stage all` で通しても動きますが、2段目が長いので分けたほうが扱いやすいです。

### なぜ話題出しを分けるのか

「ギャルの会話を作って」と繰り返し頼むと、同じ話題ばかり返ってきます。
話題を固定して振ると多様性が出ますが、**その話題リストを人間が書くと、そこが多様性の上限になります。**

そこでジャンルだけをこちらで決めて（`CATEGORIES` の20個）、
具体的な話題はモデルに列挙させています。ジャンルという骨組みだけ用意して、肉は付けさせる。
2段目では「話題 × 用件 × 機嫌」の組み合わせごとに会話を書かせるので、
話題が200件あれば8,000通りの条件ができます。

### 文体を例文で教えていないのは意図的

`STYLE` には禁止事項と話し方の仕様しか書いていません。手本のセリフは1つも入れていません。
例文を渡すと、モデルはそれを言い換えるだけになり、**手本の数だけしか語彙が広がりません。**

代わりに「一人称は うち」「敬語を使わない」「40文字を超えない」「絵文字を使わない」
のように、守るべき性質を列挙しています。

## 検査でふるいにかける

テンプレートで作っていた頃は、想定外の文字が出たら「テンプレートの書き間違い」でした。
だから見つけ次第そこで止めるのが正しい。LLM に書かせる今は事情が違います。
**モデルは一定の割合で必ず変なものを出す**ので、止めるのではなく捨てて、どれだけ捨てたかを数えます。

`validate.py` が捨てる理由は次のとおりです。

- **文字種** — ひらがな・カタカナ・漢字と、許可した記号以外を含むもの
- **英単語** — 許可リストにない綴り。実際に `treffen`（ドイツ語）が混ざっていました
- **敬語** — 文末が「です」「ます」で終わる返答。キャラクターが壊れる
- **方言** — 「ねん」「やけど」「あかん」など。関西弁が混ざると人格がぶれる
- **長さ** — 短すぎる・長すぎるもの
- **重複** — 完全一致に加えて、**返答文だけの一致も落とす**

最後の1つが効きます。LLM は違う話題を振っても同じ返しを書いてくることがあり、
それを残すと小さいモデルはその1文だけを覚えます。

### 弾く前に直す

棄却理由を数えたら、いちばん多いのが `…`（三点リーダ）でした。
日本語として何もおかしくない文字を、許可リストに入れ忘れていただけで捨てていたわけです。
全角チルダ `～` と波ダッシュ `〜` の違いのような**表記の揺れ**も同じです。

そこで検査の前に正規化を挟みました。これだけで棄却率が **42.3% から 30.7% に下がりました**。

NFKC 正規化を使っていないことに注意してください。NFKC は `！` `？` を半角に変えてしまい、
公開データ側の表記と食い違います。必要な変換だけを手で並べています。

## Macを1回落とした話

22B のモデルをバッチ24で走らせたら、macOS がカーネルパニックで落ちました。

```
panic(cpu 9): IOGPUGroupMemory.cpp:220 Assertion failed: result != kIOReturnSuccess
Panicked task ...: pid 3625: python3.11
```

Apple Silicon はユニファイドメモリなので、GPU の割り当ても本体RAMから取ります。
MLX は既定で上限を持たず、要求が通らなくなると GPU ドライバ側が確保失敗を
アサーションで扱って**カーネルごと落ちます**。Python の例外にならず、マシンが落ちる。

`runtime.py` に3つの安全装置を入れました。

1. `mx.set_memory_limit()` で明示的な上限を与える。超えたら Python の例外になる
2. 開始前にスワップ使用量を見て、余裕がなければ走らせない
3. バッチごとにピーク使用量を測り、上限に近づいたら止める

3つ目は実際に作動しました。バッチ12で 29.6GB に達したところで停止し、
「バッチを半分にして再実行してください」で終わりました。マシンは落ちていません。

## モデル選びはパラメータ数では決まらない

最初は `calm3-22b-chat` を使いました。日本語ネイティブで Apache-2.0、
しかも `magpie-sft-v1.0` を作ったモデル本人なので、系譜としても筋が通ります。

ところがバッチを4より上げられませんでした。原因は構成にあります。

| モデル | 層 | KVヘッド | KVキャッシュ |
|---|---|---|---|
| calm3-22b-chat | 48 | **48** | 1トークン 1,152KB |
| Qwen2.5-32B-Instruct | 64 | **8** | 1トークン 256KB |

calm3 は GQA（Grouped Query Attention）を持たない世代で、KVヘッドがアテンションヘッドと同数あります。
**パラメータ数は 32B のほうが多いのに、KVキャッシュは4分の1以下**です。
バッチ生成で先に足りなくなるのは重みではなくKVキャッシュ側なので、
同時に走らせられる本数はここだけで決まります。

実測は次のとおりでした。

- calm3-22b-chat（バッチ4）: 8件/分
- Qwen2.5-32B-Instruct（バッチ24）: 37件/分

`generate.py` は起動時にこの見積もりを表示します。バッチを増やす前に読んでください。

## 使いかた

検査を通したデータセットは `data/raw/gal_line.jsonl` に同梱してあります。
自分で作り直す場合だけ `--stage build` を走らせてください
（`data/raw/gal_line.jsonl` を上書きします）。

### 追加学習でキャラクターを付ける（推奨）

素の状態から学習し直すより、事前学習済みのモデルに追加学習するほうが速くて確実です。
実測で 40秒しかかかりません。

```bash
# ギャルだけのコーパスを作る
python data/prepare.py --no-hf --out data/corpus_gal.txt --min-char-freq 1

# 事前学習済みの重みから続ける
python src/train.py --init-from checkpoints/final --corpus data/corpus_gal.txt \
    --cache-dir data/cache_gal --out checkpoints/gal \
    --lr 1e-4 --warmup 12 --steps 90
```

ここで大事なことが3つあります。

**語彙を作り直さないこと。** `--init-from` を付けると、トークナイザは事前学習したものが
そのまま使われます。作り直すとIDの対応が変わり、事前学習した重みが全部無意味になります。

**低頻度文字フィルタを切ること（`--min-char-freq 1`）。** 事前学習済みのサブワード
トークナイザには byte fallback があるので、珍しい文字も表現できます。
数千件しかないコーパスで頻度10未満を捨てると、ほとんど残りません。

**混ぜる量は実測して決めること。** これがいちばん試行回数を使ったところです。
一般には「新しいデータだけで回すと破滅的忘却が起きるので元のデータを混ぜる」と言われます。
実際に測ると、そう単純ではありませんでした。

### 混ぜるほど口調が戻る

ギャルの文字数比率を変えて5通り試しました。

- **50%**（`gal:10` + `all:0.02`）── 口調が元に戻る。「こんにちは、おはよう。今日はどんな気分であなたを助けることができますか？」
- **58%**（`gal:2` + `all:0.008`）── 同じく戻る。「こんにちは！私はオープンアシスタントです」
- **85%**（`gal:3` + `all:0.002`）── 口調はギャルになるが、混ぜた公開データ側が
  117会話しかなく19エポックで丸暗記された。無関係な質問に長い定型文が丸ごと出てくる
- **89%**（`gal:5` + `all:0.0103`）── 短い返答は自然だが、公開データに頻出する質問文
  （「おすすめの本を教えてください」など）では元の文体が勝つ
- **100%**（混ぜない）── 口調は完全にギャル。**採用**

**過半では足りません。** モデルは応答の文体を、その質問に続いた文章の多数派から決めます。
「こんにちは」や「おすすめの本を」のような公開データに頻出する書き出しでは、
全体比率で負けていなくても、その質問に限って公開データ側の文体が勝ちます。

### 混ぜなくても崩れなかった（データ量次第）

会話855件の時点で混ぜずに回したときは、確かに日本語が崩れました
（「あ、そっかりでしょw」「おすすめ、スマホ見つかるから美味しくて」）。
ところが会話2,610件では、混ぜなくても崩れませんでした。

つまり**破滅的忘却の対策として最初に打つ手は、混ぜることではなくデータを増やすこと**です。
混ぜるのは、汎用の応答能力を保ちたい場合の選択肢になります。試すなら `mix_corpus.py` で
比率を指定します（`パス:繰り返し回数` の形式）。

```bash
python data/prepare.py --out data/corpus_all.txt          # 公開データセット側
python tools/mix_corpus.py --out data/corpus_ft.txt \
    data/corpus_gal.txt:3 data/corpus_all.txt:0.002
```

なお、調整すべきものは2つあります。**文字数の比率**が口調の寄り方を決め、
**それぞれが何回学習されるか**が丸暗記するかを決めます。コーパスの中でギャルを
N 回繰り返して全体を E エポック回せば、ギャルは N×E 回、公開データは E 回学習されます。
上の 85% で丸暗記が起きたのは、比率を上げるために公開データ側の E も
19 まで上げてしまったからです。

採用した設定はこれです。

```bash
python src/train.py --init-from checkpoints/final --corpus data/corpus_gal.txt \
    --cache-dir data/cache_gal --out checkpoints/gal \
    --lr 1e-4 --warmup 12 --steps 90
```

90ステップは、2,610会話（19万トークン）を約8周する量です。学習率は事前学習の
3e-4 から 1e-4 に落とします。作った表現を壊さない範囲で口調だけ動かしたいからです。

### 代償は数字に出る

固定検証セット（公開データ由来 249会話）で採点すると、こうなります。

| 指標 | 追加学習前 | ギャル版 |
|---|---|---|
| bits/char | 2.584 | **3.550**（悪化） |
| 主題保持率 | 0.733 | **0.267**（悪化） |
| 反復率 | 0.100 | **0.000** |
| 破綻率 | 0.000 | 0.000 |
| 平均返答長 | 64.1文字 | 25.1文字 |

**汎用の応答能力は確実に落ちます。** 検証セットは公開データの文体なので、
そこから遠ざかったぶんだけ bits/char は悪化します。当然の結果です。

大事なのは、この悪化が「失敗」ではなく**選択の代償として見えている**ことです。
指標を用意していなければ、「ギャルになった、成功」で終わっていました。
何を捨てて何を得たのかは、測らないと分かりません。

## 出来たもの

実測です（Qwen2.5-32B-Instruct-4bit / バッチ24 / 80分）。

- 生の出力: 3,209件
- 検査を通ったもの: **2,610会話 / 111,574文字**（棄却率 18.7%）
- 平均: ユーザー 17.3文字 / 返答 25.5文字

会話の例です。**モデルの出力**で、学習データではありません。

```
あなた> おはよう
2LM  > おはよう、うちもやってみたいよ。でも、お腹すいたから早く寝ぼけてるw
あなた> 今日バイト行きたくない
2LM  > おめでとう！でも今は腹減った〜、ごしらえしない？
あなた> AIって将来どうなると思う？
2LM  > AIのことって言ってもんけど、将来的にはまずはお腹ごしらえしないと！
```

何を聞いても腹が減っています。これはデータ側の設計がそのまま出たものです。
返答の「機嫌」を5種類（機嫌がいい / 眠くてだるい / テンションが高い /
ちょっと呆れている / 腹をすかせている）用意して均等に振っているので、
**空腹と眠気が全体の40%を占めています。** 13.8M パラメータのモデルは
そこまで細かく条件を切り分けられないので、平均的な人格として表に出ます。

意図した挙動ではありませんが、データの偏りがモデルの癖として現れる例としては
分かりやすいので、そのまま残しています。減らしたければ `MOODS` の比率を変えます。

## ファイル

| ファイル | 役割 |
|---|---|
| `generate.py` | 話題出し・会話生成・検査の3段階。止めても再開できる |
| `validate.py` | 文字種・英単語・敬語・方言・重複でふるいにかける |
| `runtime.py` | GPUメモリの上限設定と安全装置。Macを落とさないための仕掛け |
| `topics.txt` | 1段目の出力。モデルが列挙した話題（追跡対象外） |
| `raw.jsonl` | 2段目の出力。検査前の生の会話（追跡対象外） |
| `../raw/gal_line.jsonl` | 3段目の出力。検査を通った2,610会話（**同梱**） |

`raw.jsonl` を `data/raw/` に置いていないのは意図的です。あそこに置くと
`data/prepare.py` が未検査のまま拾ってしまいます。
検査を通したものだけが `data/raw/` に出ます。
